## Source of truth

Espressif publishes TRM LaTeX sources at
<https://github.com/espressif/esp-technical-reference-manual-latex>. This is the
input — **not** the compiled PDFs. A previous approach downloaded PDFs via
`download_trms.py`; both that script and `trm_pdfs/` have been deleted, since
`latex_parser.py` consumes source and the source is freely available.

Path resolution should cascade, mirroring how `build_idf_docs.sh` handles
`IDF_PATH`:

1. `$TRM_PATH` if set
2. `./trm_latex` — a gitignored local symlink (already created here)
3. `~/git/esp-technical-reference-manual-latex`

The symlink is convenience only; absolute-path symlinks don't travel between
machines, so it is gitignored and `TRM_PATH` is the portable mechanism.

Verified against HEAD `87b1c88` (2026-07-23): 1,550 English `.tex` files. The ten
chip directories (`ESP32/`, `ESP32-S2/`, `ESP32-S3/`, `ESP32-C3/`, `ESP32-C5/`,
`ESP32-C6/`, `ESP32-C61/`, `ESP32-H2/`, `ESP32-P4/`, `ESP8684/`) match every
non-null `trm_folder` in `chips.yaml` exactly, including the `ESP8684` codename
for esp32c2. `chip_vocab.chip_for_trm_folder()` already does this mapping and has
no callers yet — it was written for precisely this.

## Why source parsing is right here (and why that isn't a contradiction)

`CLAUDE.md` states the ESP-IDF lesson emphatically: never parse `.rst`, always
consume the build. That lesson does **not** transfer to the TRM, and it is worth
being explicit about why, so nobody "fixes" this later by trying to run LaTeX.

ESP-IDF needed a build because its content dependencies are *deep*: constants
extracted from `soc_caps` headers, Kconfig values, `only::` branches selected per
target, and an entire API reference generated by doxygen from C sources. None of
that is recoverable from the `.rst` text.

The TRM's build-time dependencies are *shallow*:

- **File inclusion** — `\subfile{...}` and `\input{...}`, mechanically resolvable.
- **A few `\def`'d values** — e.g. `\chipname`, defined in
  `00-shared/config/preamble-trm-repo.sty`, and `\modulefiles` (a path prefix).
- **No compiler.** Nothing is extracted from another language's toolchain.

**`\ifglobal` does not gate content.** Reading the branches in
`ESP32-C3/01-I2C__EN.tex`, both `\ifglobal` blocks only choose a `\documentclass`
and front matter (TOC, todo lists). Real content begins after `\begin{document}`
at `\chapter{...}`, and this holds repo-wide.

Content branching does exist, but narrowly: `\iftagged` in 48 of 1,550 files,
concentrated in ESP32-P4. It has to be evaluated rather than flattened, exactly
as `only::` did — see resolved question 3. It does not change the conclusion
above, because evaluating it needs a tag lookup, not a compiler.

Running the real toolchain would also be a step backwards: the repo builds with
TeX Live, `minted`, Ghostscript and proprietary fonts, and produces **PDFs** —
less structure than the LaTeX source, not more.

## Chunking strategy: tree descent, not assemble-then-split

The natural document tree is *already* at chunk granularity. Measured across all
ten chips:

| Unit | n | p50 | p90 | max | ≤400 words |
|---|---|---|---|---|---|
| `register` environment | 11,531* | 36 w | 146 w | 497 w | ~100% |
| Heading unit (chapter/section/subsection) | 9,231 | 96 w | 369 w | 2,560 w | 91.5% |
| Leaf `.tex` file (register/table subfiles) | 1,153 | 411 w | 2,181 w | 39,303 w | ~50% |
| Chapter `.tex` file | 390 | 2,980 w | 7,513 w | 17,181 w | ~0% |

\* Size distribution measured over the `__EN.tex` subset only. The true
population reachable via the include graph is ~13,700 — see phase 1 on filename
filtering. The extra registers are ordinary ones on ESP32/ESP32-S2, so the shape
of the distribution holds; only the count is understated.

Two conclusions follow.

**Do not chunk at file granularity.** Chapter files are 7–43× the 400-word cap.
Leaf files look promising at the median but have a long tail, because a single
register file holds many registers — p50 **16** registers per file, max 247. File
boundaries are an artifact of how authors organise source, not of meaning.

**Do build an accurate tree and descend it.** With headings and register
environments as nodes, 91.5% of heading units and essentially 100% of registers
already fit under the cap. `chunking.build_chunks` is already written this way —
it keeps a subtree whole while it fits and only splits when oversized. So there is
no new chunking algorithm to write; splitting is the fallback for the ~8.5% tail,
and it stays that way. The work is **producing a faithful tree**, not devising a
split strategy.

This also means a "are subfiles already chunk-sized?" pre-process isn't worth
building: the table above already answers it (no, not reliably), and the answer
doesn't change the design, because the tree is the right structure regardless.

### Registers need to be atomic

A register is an indivisible record — name, address, bitfields, per-field
descriptions. Two consequences:

- **Never split one.** `_split_oversized_block`'s line-grouping heuristic would
  cut a large register mid-bitfield, stranding fields from the register name that
  gives them meaning. `chunking.Block.atomic` exists for this and
  `_split_paragraphs_with_refs` honours it. The IDF side benefits too — API
  `desc` blocks have identical semantics.

  This is **not** a theoretical safeguard. An earlier draft of this document
  claimed every register fits under the cap, so atomicity would rarely fire —
  that was wrong, and wrong for the familiar reason: the size table below was
  measured over the `__EN.tex` subset. **28 registers exceed 400 words on their
  own** (largest 518, not the 497 stated below) and hit the splitter directly.
  Verified by a control: `UART_CONF0_REG` (448 words, `ESP32/19-UART__EN.tex`)
  survives whole with the flag and is cut without it.
- **Merging adjacent registers is fine.** At p50 36 words they fall below
  `MIN_WORDS_PER_CHUNK`, so `merge_undersized_chunks` will group them. That is
  desirable: consecutive registers belong to one peripheral and share context.
  Merge yes, split no.

## Macro coverage — the main body of work

`latex_coverage_check.py` on ESP32-C3 alone (126 files): **100 unknown macros, 14
unknown environments**. Across the full repo: ~240 and ~28. The parser was clearly
written against a small sample. The count overstates the difficulty — grouped by
what they actually demand:

**Ignorable (drop or pass through).** `\centering` (189), `\bfseries` (158),
`\it` (101), `\textcolor` (168), `\rotatebox` (122), `\fbox` (40),
`\scriptsize`, `\includegraphics` (126, alt text unavailable — drop), and
`bytefield` (see resolved question 1 below — a diagram package, not registers).

**Preamble scaffolding (skip everything before `\begin{document}`).**
`\documentclass` (69), `\usepackage` (43), `\newif`/`\globaltrue`/`\ifglobal`/
`\else`/`\fi`, `\myexternaldocument` (35), `\selectlanguage`, `\setcounter`,
`\let`, `\relax`, `\def`, `\tableofcontents`.

**Must handle — content is lost otherwise.**

- `\subfile` (73) / `\input` (36) / `\modulefiles` (162) — the inclusion problem.
  Register content lives exclusively in included files. **This is the single
  highest-priority item**; without it the most valuable TRM content is absent
  and nothing in the output would indicate it.
- `\verb` (291) — inline verbatim, needs its own lexing (delimiter is the next
  character).
- `\endhead` (85) / `\endfirsthead` (51) / `\endfoot` (51) / `\endlastfoot` (34) —
  `longtable` repeated-header machinery. Currently unhandled, which means header
  rows get duplicated into body content.
- `\tnote` (111) + `threeparttable` / `ThreePartTable` / `tablenotes` — a second
  table family beyond the `longtable`/`tabular` that `_render_table` knows.
- `math` / `equation` / `gather*` (3,640+ repo-wide) — TRM prose contains real
  inline math (e.g. the `$R/\overline W$` bit in the I2C overview).
- `\caption{...}` — 1,703 of 1,754 `figure` environments (97%) carry a caption,
  and they are descriptive ("UART Architecture Overview", "GDMA Engine
  Architecture", "TDM PCM Standard Timing Diagram"). The figure image itself is
  unrecoverable, but the caption is real text and cheap to extract. Do it.
- `\chipname` (163) / other `\def`'d values — expand from
  `00-shared/config/preamble-trm-repo.sty`, or the literal macro name lands in
  the embedding. This is the TRM's `{IDF_TARGET_*}` analogue.
- `\iftagged` (169 across 48 files) — **must be evaluated, not flattened.** The
  one genuine content-gating conditional in the corpus, and it leaves `register`
  environments syntactically unbalanced. See resolved question 3.

## Phases 1-2 as built

`resolve_document(path) -> ResolvedDocument` and `chunk_document(path) ->
(chunks, doc)` are the entry points; `chunk_latex(text, file_path)` still works.
The pre-pass runs on raw text before pylatexenc, in this order: mask comments →
strip preamble → resolve `\ifglobal`/`\iffalse` → select tags → lift body
definitions → splice includes recursively. Misses and cycles land in
`ResolvedDocument.missing` rather than being swallowed.

Verified independently of the agent that wrote it: **13,597/13,597 registers,
exact on all ten chips, zero unresolved includes.** Capture rate 96.7% across the
379 chapter roots, worst file 77.2%; the residue is reference-side tokenisation
noise (column specs like `p{1.8cm}`, `\cline{3-7}` ranges), not content loss.
`ESP32-P4/56-LEDPWM__EN.tex` — the `\iftagged` case — yields 20 registers from 27
`\begin{register}`, correctly selecting the `0-7` branch rather than ESP32-C61's
`0-5`.

**Reconciling two register counts.** `register_census.py source` reports
**13,707** because it greps `\begin{register}` before tag selection; the parser
emits **13,597** after it. The 110-register difference is unselected `\iftagged`
branches and is *correct*. It is 0.8%, comfortably under the census's 2%
threshold, so a faithful ingest still passes — but don't go hunting for the gap.

**Three bugs surfaced that this plan did not anticipate**, all invisible in word
counts, all of the "silent corruption" class this project keeps meeting:

1. **`&` was being dropped**, so `_render_table`'s `split("&")` never split and
   *every table row rendered as one run-on cell*. Pre-existing.
2. **A `\newcommand` body opening an environment closed at the use site.** The
   GPIO chapters define a macro containing `\begin{small}\begin{longtable}…`
   with no `\end`; pylatexenc scanned for the missing `\end{small}` and swallowed
   **128,896 characters — 221 registers vanished with no error.**
3. **`lstlisting` was shredded**, because pylatexenc's verbatim parser hardcodes
   `\end{verbatim}`, so listing bodies were parsed as LaTeX.

## Remaining phases

**1. Inclusion resolution.** Pre-pass expanding `\subfile`, `\input` **and
`\subfileinclude`** (878 occurrences — a third include macro; missing it loses
whole chapters) after substituting `\def`'d path macros, recursive with a cycle
guard. Skip everything before `\begin{document}`. **Strip LaTeX comments first**:
chapter headers contain literal commented-out examples like
`% '\input{\modulefiles/tables/---.tex}'`, which otherwise produce 900+ phantom
unresolved includes and render the missing-include report useless.

**Document roots are the 379 numbered `NN-NAME__EN.tex` chapter files only.**
Per-chip aggregators DO exist — `ESP32-C3/ESP32-C3-main__EN.tex`,
`ESP32-P4/ESP32-P4-chip-revision-v1.3__EN.tex` and similar `\subfileinclude`
every chapter. Treating every top-level `*__EN.tex` as a document ingests each
manual 2-3 times over.

**Filter to English at the root level only — never filter includes by filename.**
Included subfiles do not all follow the `__EN`/`__CN` convention: ESP32,
ESP32-S2 and ESP8684 use lowercase `_en.tex`/`_cn.tex` (e.g.
`ESP32/24-ETHERNETMAC/ethernet_reg_en.tex`), holding **1,476 registers** that a
`__EN.tex` filter drops silently. Follow the include graph and take whatever path
the include names.

**2. Macro coverage** to a measured bar, driven by `latex_coverage_check.py` run
across all ten chips rather than one. Treat anything appearing >50 times as
required.

**3. Port onto `chunking.py`.** Replace `latex_parser.Chunk` and its bespoke
section-stack (`latex_parser.py:275-336`) with `SectionNode`/`Block`, then call
the shared `build_chunks`/`merge_undersized_chunks`. This is why `chunking.py`
was made source-agnostic. Prose maps directly; `_render_table` already emits a
flat blob suited to `Block.text`; registers become atomic blocks per above.
`Refs` has no LaTeX equivalent yet — `\label`/`\hyperref` extraction into
`doc_refs` is optional follow-up work, not required for a first cut.

**4. `ingest_trm.py`.** Mirror `ingest_sphinx_xml.py`: walk chip dirs, resolve the
chip via `chip_vocab.chip_for_trm_folder()` on the directory name, write JSONL.
**No dedup step** — one manual per chip, so `dedup_chunks.py` does not apply.
Then `embed_and_store.py --doc-type trm --chip <chip>` once per chip. TRM rows
populate the singular `chip` column and leave `chips` empty, which is what
`mcp_server._build_where` already expects.

**5. Verification** — gates everything above, per `CLAUDE.md`'s "verify output,
don't trust counts":

- **Capture rate per file**: extracted words vs. the source's own text content.
  This is the method that caught the `field_list` bug on the IDF side, where
  4,222 nodes were being silently dropped while totals looked healthy.
- **Coverage gate**: `latex_coverage_check.py` across all chips, with a hard look
  at anything frequent remaining unknown.
- **Register spot-checks**: assert known registers survive intact — e.g.
  `I2C_SCL_LOW_PERIOD_REG` at `0x0000` in
  `ESP32-C3/01-I2C/01-I2C-reg__EN.tex` — name, address and every bitfield in one
  chunk.
- **Register census**: ~13,700 register environments are reachable through the
  include graph (a naive `__EN.tex` grep gives only 11,539 — if a census lands
  near that number it is dropping ~2,000 registers, mostly ESP32/ESP32-S2).
  Count how many survive into chunks, **per chip**, since the failure modes are
  chip-specific: filename convention on ESP32/ESP32-S2, `\iftagged` on ESP32-P4.
  `register_census.py` implements this and exits non-zero past a shortfall
  threshold.
- Register names nest braces (`SPI\_MEM\_C\_{n}\_REG` for register banks, ~17%
  of all registers). A non-nesting `\{[^}]*\}` capture truncates them, which
  reads downstream as missing registers. Match with brace balancing.
- `check_thin_files.py latex` covers the capture-rate side (`xml` remains for the
  IDF corpus — they are separate subcommands because a Sphinx page is one
  self-contained file whereas a TRM chapter is a `.tex` plus everything it
  includes).

### The checkers are themselves tested

`make_trm_fixture.py` synthesises two corpora from the real LaTeX: `--mode good`
expands the include graph, `--mode broken` uses only each chapter's own body,
simulating unresolved includes — the exact failure that would strip the register
content living in included files. Measured discrimination:

| | register census | capture rate |
|---|---|---|
| `--mode good` | 100.0% (10,099/10,100), exit 0 | median 92%, nothing flagged |
| `--mode broken` | 2.2% (223/10,100), exit 1 | median 52%, 177 files flagged |

So the thresholds are calibrated against real data rather than guessed, and a
regression in either checker is detectable. Regenerate and re-run both after
changing either. The fixture must cover **all** chips (its default):
`register_census.py` compares against the whole corpus, so a single-chip fixture
reports a catastrophic shortfall when nothing is wrong.

## Resolved questions

All three were investigated against the source and independently spot-checked.

**1. `bytefield` is not a second register representation — scope unchanged.**
31 occurrences in 6 files, confined to ESP32 (21), ESP32-P4 (4), ESP32-S2 (2) and
ESP32-S3 (2); zero in C3, C5, C6, C61, H2 and ESP8684. Every occurrence sits
inside a `\begin{figure}`, and the usage is CPU *instruction encoding* (ULP
coprocessor opcode layouts) or DMA *descriptor* layouts — not memory-mapped
peripheral registers. Those same chapters carry their real registers in
`\subfile`d `-reg__EN.tex` files using the ordinary `register` environment
(e.g. 59 in `ESP32/24-ETHERNETMAC/ethernet_reg_en.tex`). Against a repo total of
**11,539** `register` environments, ignoring `bytefield` loses no register
content. Treat it as a diagram, i.e. ignorable.

**2. Figures lose no register data, but captions are worth extracting.** No case
was found where a register bit layout exists *only* as a figure: every
register-ish figure duplicates a `register` environment or table documented
in the same chapter. The figure population is overwhelmingly block/architecture
and timing diagrams. 97% of figures carry a caption, so extract `\caption{...}`
(see phase 2) and accept that the images themselves are unrecoverable.

**3. `\ifglobal` never gates content — confirmed repo-wide.** Every chapter file
has exactly one `\begin{document}`, always unconditional and after the single
`\fi`. The conditional's branches contain only `\documentclass`, `\usepackage`,
`\myexternaldocument` and comments. Skipping the preamble is safe.

**But `\iftagged` DOES gate content — this document previously claimed otherwise
and was wrong.** `\iftagged{<TAG>}{<true>}{<false>}` (etoolbox) selects between
alternative content at build time. Verified in English files: **169 occurrences
across 48 files** — ESP32-P4 127, ESP32-H2 21, ESP32-C5 18, every other chip 0 —
and **9 of them wrap a `\begin{register}`**. Example, from
`ESP32-P4/56-LEDPWM/56-LEDPWM-reg__EN.tex:1`:

```latex
\iftagged{ESP32-C61}{\begin{register}{H}{LEDC\_CH\regindex{n}\_CONF0\_REG (\regindex{n}: 0-5)}{...}}%
                    {\begin{register}{H}{LEDC\_CH\regindex{n}\_CONF0\_REG (\regindex{n}: 0-7)}{...}}
```

Two different register definitions — channels 0-5 versus 0-7 — one chosen by tag.
This is a real analogue of the ESP-IDF `only::` failure mode: flattening both
branches yields duplicated, mutually contradictory register definitions in one
chunk. **`\iftagged` must be evaluated, not flattened.** Note the tag may name a
different chip than the containing directory (the example lives under `ESP32-P4/`
but tags on `ESP32-C61`), so the selection semantics need establishing from the
sources rather than assuming tag == containing chip.

It also breaks the source syntactically: each such construct has two
`\begin{register}` but one `\end{register}`, since only one branch survives
compilation. Repo-wide that is 11,538 `\begin{register}` against 11,531
`\end{register}`; `56-LEDPWM-reg__EN.tex` alone has 27 versus 20. A parser that
assumes balanced environments may error, mis-nest, or silently swallow the rest
of the file — the last being the dangerous outcome.

The scale is small (169 sites against 11,539 registers) but it is concentrated in
ESP32-P4, the largest manual, so the register census must be checked per chip and
not just repo-wide.

## Decided: ingest both P4 variants and deduplicate

**Ingest every variant, dedup by `(file_path, text)`, and record applicability in
a `revisions` list column** — the same mechanism `chips` already uses, one axis
over. Content common to both variants stores once listing both; content that
differs stays separate and correctly narrower.

This is not optional polish. The register sets diverge **in both directions**:

| | registers |
|---|---|
| Common to both | 2,873 |
| Only in v1.3 | **48** |
| Only in mainline | **60** |

Picking a single variant silently loses real registers either way — v1.3's
`AHB_DMA_ARB_TIMEOUT_RX_REG`/`TX_REG` became one `AHB_DMA_ARB_TIMEOUT_REG` in
mainline. Someone debugging v1.3 silicon against mainline-only docs would be
looking up a register their part does not have. Distinct register-env counts
(3,977 vs 3,990) also show same-named registers whose bitfields changed, which
only text-level dedup catches — name comparison would miss them.

The alternative of two pseudo-chips (`esp32p4`, `esp32p4-v1.3`) was rejected: it
duplicates ~2,873 identical registers plus surrounding prose in the largest
manual, returns every P4 result twice, pollutes `esp32_docs_list_chips` with
something that is not a chip, and breaks the `chip_vocab` validation contract.

### Labels: `v1.3` and `mainline`, never "latest"

The source names them itself, in `ESP32-P4/00-chip-spec-content/chip-spec-settings.sty`:

```latex
\newcommand\chiprevisionEN{%
    \untagged{ESP32-P4-latest}{Chip Revision v1.3}%
}%
```

Untagged builds are titled "Chip Revision v1.3"; the tagged build carries **no
revision qualifier at all** — it is the mainline manual. `ESP32-P4-latest` is the
tag's internal name and was never a published label, so storing "latest" would
invent a version string Espressif does not use *and* rot the moment new silicon
ships. Store `v1.3` and `mainline`, and let `source_commit` pin down what
`mainline` meant at ingest time.

### Deriving the variant

Drive it from the aggregator documents, not hand-passed tags. Each declares its
own tag set:

- `ESP32-P4-main__EN.tex` → `\usetag{ESP32-P4-latest}` → `revisions=["mainline"]`
- `ESP32-P4-chip-revision-v1.3__EN.tex` → no tag → `revisions=["v1.3"]`

Chapters are still ingested individually (the 379 numbered files), but the tag
context comes from the aggregator, so nobody has to remember to pass
`extra_tags`. Chips with a single manual get `revisions=["mainline"]` so
`array_contains` works uniformly — do not leave it empty for them, or the
empty-list trap that `chips` was redesigned to remove reappears here.

Note the other tags (`ESP32-C61`, `ESP32-C5`, `ESP32-S31`, `ESP32-H21`,
`ESP32-H4`) are a *different* use: chip selection inside shared register files,
already handled by `\usetag{\chipseries}`. Only `ESP32-P4-latest` is a revision
axis.

## Superseded: the original open question

Tags are declared by `\usetag{\chipseries}` in
`00-shared/config/preamble-trm-repo.sty` — so a chip's own name is always an
active tag — plus `\usetag{ESP32-P4-latest}` in `ESP32-P4-main__EN.tex`. There
are also two-argument `\tagged`/`\untagged` forms, not just `\iftagged`; 170 uses
of `\tagged{ESP32-P4-latest}` alone.

Because a standalone chapter build activates only `{<chipname>}`, ESP32-P4-latest
content is currently **excluded**, i.e. the ingest would capture the v1.3 base
variant. `resolve_document(..., extra_tags=...)` accepts an override. Whoever
writes `ingest_trm.py` must decide: ingest the base variant, pass
`{'ESP32-P4-latest'}`, or ingest both and let `chips`/metadata distinguish them.
Ingesting both risks near-duplicate registers differing only by revision.

## The 8 "missing" registers are a checker artifact, not content loss

`register_census.py check` reports 8 registers missing on a full ingest. **All
eight are `trm_verify` counting source the parser is right to exclude.** The
parser loses nothing.

- **6 registers sit inside `\iffalse … \fi`** — `AES_ENDIAN_REG`,
  `AES_AAD_BLOCK_NUM_REG` and `AES_REMAINDER_BIT_NUM_REG`, in both
  `ESP32-C3/24-AES` and `ESP32-S3/30-AES` (see `24-AES-reg__EN.tex:8,57`).
  Deliberately disabled upstream. `latex_parser` evaluates the conditional;
  `trm_verify` does not, so it counts them.
- **2 registers sit inside `\tagged{ESP32-H21}{…}`** —
  `USB_SERIAL_JTAG_SERIAL_EP_TIMEOUT0/1_REG` in
  `ESP32-H2/33-USBSERIALJTAG-reg__EN.tex:360`. That is content for **ESP32-H21, a
  different chip**; including it in the H2 manual would be a correctness bug.
  Both resolvers reach the same file set — the divergence is inside the text.

Fixing this properly means teaching `trm_verify.expand_document` about `\iffalse`
and about `\tagged` with an inactive tag. Until then the census will keep
reporting 76.9% for the two AES chapters and 93.3% for `ESP32-H2/33-USBSERIALJTAG`,
and that is the expected reading rather than a regression.

**A cautionary note on how this was originally diagnosed.** An earlier version of
this section claimed the six AES registers failed to render because their names
contain nested braces (`\regindex{n}`). That was wrong. The registers render
correctly and always did — `Register AES_KEY_n_REG (n: 0-7) at address
0x0000+4*n`. The "evidence" was a regex, `Register (AES_[^\s]+) at address`,
which cannot match a register name containing a space, so every parameterised
register looked absent. Nested-brace parsing works fine throughout; pylatexenc
returns all three arguments intact. When a check says content is missing,
confirm the *check* before writing down a cause.

## Fixed: line-wrapped register headers

One real defect existed and is fixed. `_render_register` preserved a source
line-wrap inside an argument, so a register whose name is written across two
lines emitted its address on the block's second line, where every line-wise
consumer read the header as address-less:

```latex
\begin{register}{H}{MCPWM\_TIMER\regindex{n}\_SYNC\_REG⏎(\regindex{n}: 0-2)}⏎{0x000C+0x10*\regindex{n}}
```

`_render_one_line` now collapses newlines for header fields (register name,
address, and each `\regfield` name/width/bitpos/reset). Both MCPWM registers now
render as `Register MCPWM_TIMERn_SYNC_REG (n: 0-2) at address 0x000C+0x10*n`.
A full text diff of all 13,597 rendered registers shows exactly **6 changed**,
all intended: the 2 MCPWM headers rejoined, and 4 RISC-V `pmpXcfg` blocks that
genuinely have an empty address argument upstream now rendering `Register X`
rather than a dangling `Register X at address `. Parameterised registers went
from 1,154/1,156 to **1,156/1,156** rendering with name and address.
